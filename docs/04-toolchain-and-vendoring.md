# 04 — JieLi toolchain & vendored blobs

## The real toolchain (recommended over Ghidra for disassembly)

`scripts/setup_toolchain.sh` installs JieLi's official Linux toolchain into
`/home/yukidama/JL/toolchain` (outside the git repo):

| Package | Source | Contents |
|---|---|---|
| `jieli-linux-toolchains-*` | https://pkgman.jieliapp.com/s/linux-toolchain | Clang/LLVM 4.0.1 cross-compiler with `pi32` / `pi32v2` / `q32s` backends, libc/libm/compiler-rt |
| `jieli-linux-post-build-tools-*` | https://pkgman.jieliapp.com/s/linux-postbuild | firmware packer / listing / download tools |

Docs: https://doc.zh-jieli.com/Tools/zh-cn/dev_tools/build_download/index.html

Layout (`…/jieli-linux-toolchains-YYYYMMDD.N/`):
```
common/bin/    clang objdump objcopy   (LLVM driver + binutils)
pi32v2/bin/    cc cxx clang as ld ar nm strip objsizedump   (target drivers; cc is a py wrapper -> clang -target pi32v2)
pi32v2/lib/    libc.a libm.a libg.a libcompiler-rt.a  + r1..r5[/-large] ABI variants
pi32v2/include/
```

The compiler emits Blackfin-style *algebraic* assembly (`r0 += r1`,
`ifs (r0 < 1) { … }`, `r3_r2 = r2 * r1 (u)`, `rep n rN { … }`), and objects are
`ELF32-pi32v2`, **ELF machine `0xf1` (241)** — matching ghidra-jieli's opinion
file.

### Authoritative disassembly with the vendor objdump

The vendor `objdump` decodes this ISA more accurately than the (early-stage)
ghidra-jieli SLEIGH module. Wrap `app.bin` in an ELF section and disassemble:

```bash
TC=/home/yukidama/JL/toolchain/toolchain/jieli-linux-toolchains-*/
printf '\t.section .fw,"ax",@progbits\n_fw:\n\t.incbin "app.bin"\n' > wrap.S
$TC/pi32v2/bin/cc -c wrap.S -o wrap.o
$TC/common/bin/objdump -d --section=.fw wrap.o > app_pi32v2_objdump.txt
```

Result: **211 252 instructions** and **2 062 function entries** (12 038 `call`
sites), vs SLEIGH's 162 848 / 1 960 / 9 365. The difference is the `80 ff …`
long-form `call` prefix: SLEIGH mis-splits it into `testset b[r0]`+`nop`, which
is exactly why SLEIGH flow-following broke. Example (offset 0x10):

```
vendor:  80 ff b0 00 00 00   call 0x020000C6      ← correct
sleigh:  b0 00 / 00 00       testset b[r0] / nop  ← wrong
```

→ `analysis/disassembly/app_pi32v2_objdump.txt` (authoritative listing),
`analysis/disassembly/function_entries_vendor.csv` (2 062 entries ranked by call count).

**Recommendation:** use the vendor objdump listing as the source of truth for
function boundaries and code, and keep the Ghidra/SLEIGH path for its
bidirectional Assembler (byte-identical round-trip, doc 02). A worthwhile
follow-up is teaching ghidra-jieli the `80 ff` long-call prefix, which would
both fix the mis-decodes and unblock recursive analysis/decompilation.

## Vendored component provenance

The package also contains JieLi-produced components whose SDK lineage helps
interpret the stock application and boot chain:

| Blob | Where it comes from |
|---|---|
| `top/uboot.boot` (SPL, "UBOOT2.00") | AC791N/WL82 SPL, byte-matched to the AC79 SDK tag documented in `analysis/device/uboot/README.md` |
| `files/cfg`, `files/cfg_tool.bin` | generated by the post-build config tool from `isd_config.ini` |
| Bluetooth stack (BTStack, A2DP, AVRCP, HFP…) | JieLi BT SDK, shipped as `.a` libraries + headers, linked into the app |
| BLE / OTA (`ble_ota.bin`) | JieLi SDK BLE-OTA component |
| ROM / mask-ROM routines (calls to `0x01Cxxxxx` / negative targets) | on-chip mask ROM; provided as import stubs by the SDK linker script |

### Where to get the BT SDK sources/libs

The embedded build stamps (`INCLUDE_BTSTACK`, `JL_A2DP`, `JL-BR22`) identify
Bluetooth-library lineage, while package and SPL provenance identify the
physical target as AC791N/WL82:

- **fw-AC63_BT_SDK** — https://github.com/Jieli-Tech/fw-AC63_BT_SDK
  (dual-mode BT SDK for the BR2x/AC63 family; contains the closed BT stack as
  prebuilt `cpu/br22/…/*.a` libraries plus open application/framework source).
- **fw-AC79_AIoT_SDK** — https://gitee.com/Jieli-Tech/fw-AC79_AIoT_SDK
  (official AC791N/WL82 headers, boot/update code, libraries, and examples).
